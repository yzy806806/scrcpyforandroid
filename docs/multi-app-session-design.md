# 多应用会话模式（Virtual Display Multi-Session）设计文档

> 状态：**已定稿**（2026-10-07）—— 可开工
> 决策记录见 §11；前置验证结论见 §2（全部为被控端真机实测）
> 目标：把「一次性屏幕镜像」升级为「多应用挂机 + 随时查看」的会话管理器

---

## 1. 需求

主控端（手机）管理被控端（手机）的**多个应用同时运行**，用途混合（游戏挂机、微信小号看消息等）。

**核心需求**：

1. 打开 app 自动连接上次的设备，直接显示**应用列表**
2. 点应用 → 在被控端启动/切到该应用，主控端查看
3. 最多 **4 个应用同时运行**（占四个挂机位）
4. 停在列表时**保持投屏**
5. **主控端退出/切后台，被控端应用继续运行**（不中断）
6. 主控端 UI：上方收藏应用格子 + 下方四宫格画面；单击格子选中、双击全屏
7. 全屏页悬浮球：**切换下一个应用**、**回退主页面**（悬浮球原有功能一律保留）
8. 返回键/返回手势**不拦截**，继续注入被控端
9. 操作：关闭选中应用（force-stop）、进入被控端真实屏幕镜像

## 2. 前置验证结论（真机实测，被控端 Android 16）

| # | 验证项 | 结果 |
|---|---|---|
| 1 | 虚拟显示创建 | `New display: 1080x2378/480 (id=136)` |
| 2 | 应用启动到指定虚拟显示 | `am start --display <id>` 生效，主屏为空 |
| 3 | 游戏在虚拟显示上渲染 | ✅ 某 Unity 手游启动页画面正常，无黑屏/花屏 |
| 4 | 游戏在虚拟显示上的状态 | `topResumedActivity` —— 前台，不被暂停 |
| 5 | 多个虚拟显示并存 | ✅ 4 个（id 145/146/147/148）+ 主屏 = 5 个显示 |
| 6 | 虚拟显示可被独立客户端投屏 | ✅ 客户端 B 成功投客户端 A 创建的显示 |
| 7 | 创建者退出后显示是否存活 | ❌ **随创建者销毁** → 必须常驻 holder |
| 8 | 断开后应用是否保活 | ✅ 进程存活，移回主显示（`--no-vd-destroy-content`） |
| 9 | 单独截取某个虚拟显示 | ✅ `screencap -d <SF-id>`，尺寸正确 |
| 10 | 4 路 540p 编码的 CPU 开销 | ✅ `800%cpu 11%user 22%sys` → 722% idle |
| 11 | 4 路并发时的编码器 | ✅ **4 路全部** `c2.mtk.avc.encoder`（硬件），无一退化软编 |
| 12 | 软件编码对照 | 单路软编 `22%user 48%sys` = 70% CPU，**约为硬件编码的 9 倍** |

**关键推论**：

- 「主控端退出后应用继续跑」**不能靠 scrcpy 自身**（server 生命周期绑定客户端连接）→ 必须有独立于主控端的常驻进程持有虚拟显示
- 4 个挂机位在显示数量上没有系统限制，**瓶颈只有内存和端口**
- 虚拟显示分辨率必须**与原机一致**（1080×2378/480），否则应用可能行为异常；「传输分辨率」是另一回事（视频流编码尺寸，可自由缩放）

## 3. 架构

```
┌────────────────────── 被控端（root + Magisk）──────────────────────┐
│                                                                    │
│  Magisk 模块                                                       │
│   ├── tunnel-server (quic-go, 已有)                                │
│   │     22289/udp · PSK 认证 → 转发 127.0.0.1:5555 (adbd)          │
│   ├── display-holder (新增, app_process + Java)                    │
│   │     ├── 创建 / 持有 N 个虚拟显示（原生分辨率）                  │
│   │     ├── 状态写入 state.json（供主控端读取）                     │
│   │     ├── 接受命令（launch / kill / create / destroy）            │
│   │     └── 被守护进程拉起，自身被 kill 时自动重启                   │
│   └── service.sh（开机启动 + 监活）                                │
│                                                                    │
│   虚拟显示 × 4  ←── 各跑一个应用（游戏 / 微信 / …）                 │
│         ↑ app 在各自显示上是前台 → 游戏逻辑持续运行                 │
└────────────────────────────────────────────────────────────────────┘
                            ↑ QUIC 隧道（adb 控制 + 视频流）
┌────────────────────── 主控端（Android app）──────────────────────┐
│   ├── 首页：收藏应用格子 + 四宫格挂机画面                           │
│   ├── 4 路 scrcpy session（--display-id 投 holder 的显示）          │
│   ├── 全屏页：悬浮球（切换下一个 / 回主页面）+ 原有全部功能          │
│   └── 会话管理：**只连接、不创建** → 应用生命周期与主控端完全解耦     │
└────────────────────────────────────────────────────────────────────┘
```

**架构要点**：主控端**不再创建**虚拟显示，只连接 holder 已持有的显示。这一条换来了「主控端随时连、随时断，应用照常跑」。

## 4. display-holder 设计（Magisk 模块侧）

### 4.1 职责

| 职责 | 说明 |
|---|---|
| 创建虚拟显示 | 原生分辨率 + 原生密度，最多 4 个（slot 0~3） |
| 持有生命周期 | 进程常驻（阻塞），显示不随主控端断开而销毁 |
| 状态暴露 | 写 `state.json`，主控端读它知道每个 slot 的显示 id 和在跑的应用 |
| 接收命令 | 通过命令文件或 Unix socket 接受 launch / kill / create / destroy |
| 被守护 | 模块 service.sh 监活；holder 自身被 kill 后自动重建显示 |

> holder 用 `app_process` 运行，机制与 scrcpy server 相同（已实测：scrcpy server 正是以 `app_process / com.genymobile.scrcpy.Server` 方式运行并成功创建虚拟显示）。**不编码视频**，开销远小于 scrcpy server。

### 4.2 状态文件

`/data/local/tmp/display-holder/state.json`

```json
{
  "version": 1,
  "pid": 12345,
  "slots": [
    { "slot": 0, "displayId": 145, "package": "com.example.game",  "state": "running" },
    { "slot": 1, "displayId": 146, "package": "com.example.chat",  "state": "running" },
    { "slot": 2, "displayId": -1,  "package": "",                  "state": "empty"   },
    { "slot": 3, "displayId": -1,  "package": "",                  "state": "empty"   }
  ]
}
```

### 4.3 命令接口

命令文件：`/data/local/tmp/display-holder/cmd`（追加一行执行一条）

```
launch <slot> <package>     # 在 slot 的虚拟显示上启动应用
kill <slot>                 # force-stop 该应用并清空 slot
create <slot>               # 按需创建该 slot 的虚拟显示
destroy <slot>              # 销毁该 slot 的虚拟显示
status                      # 立即刷新 state.json
```

选文件而非 socket 的原因：主控端本来就通过 adb shell 通道操作（隧道已具备），`echo ... >> cmd` 最简单可靠。

### 4.4 与现有模块的关系

在同一 Magisk 模块内扩展（复用开机启动、iptables 加固、守护逻辑），**不引入第二个模块**。holder 的二进制（dex）与 tunnel-server 一起放在模块目录。

## 5. 主控端改造

### 5.1 首页 UI

```
┌──────────────────────────────────────────┐
│ ● 被控设备 已连接 · 隧道 34ms      [⚙]    │  ① 状态条
├──────────────────────────────────────────┤
│  我的应用                          编辑 › │  ②
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐  ┌────┐    │
│  │ 游戏│ │ 微信│ │ …  │ │ …  │  │ + │    │  ③ 收藏（点击=占用一个 slot 启动）
│  └────┘ └────┘ └────┘ └────┘  └────┘    │
├──────────────────────────────────────────┤
│  挂机中  2/4                              │  ④ 计数
│  ┌───────────────┐ ┌───────────────┐     │
│  │▣ 游戏      ●  │ │  微信      ●  │     │  ⑤ 四宫格：单击=选中(▣) / 双击=全屏
│  │   [1fps 画面]  │ │   [1fps 画面]  │     │
│  └───────────────┘ └───────────────┘     │
│  ┌───────────────┐ ┌───────────────┐     │
│  │  ＋ 空位       │ │  ＋ 空位       │     │
│  └───────────────┘ └───────────────┘     │
├──────────────────────────────────────────┤
│  [📱 手机主页]  [✕ 关闭选中]  [⏻ 断开]     │  ⑥ 操作栏
└──────────────────────────────────────────┘
```

**交互定义**

| 元素 | 动作 | 行为 |
|---|---|---|
| 收藏格子 | 单击 | 占用一个空 slot：`launch <slot> <pkg>`，该 slot 开始投屏 |
| 收藏格子 | 长按 | 进入编辑（移除 / 排序） |
| 「+」 | 单击 | 打开应用选择器（从被控端拉取已安装列表） |
| 四宫格 | 单击 | 选中（高亮边框），操作栏「关闭选中」作用于它 |
| 四宫格 | 双击 | **全屏 + 该路重连升级画质**（投屏重连 ~1~2 秒；被控端应用不受影响） |
| 「手机主页」 | 单击 | 新建一路投 display 0 的 session，全屏显示真实屏幕。**不占 slot、按需创建、退出即销毁** |
| 「关闭选中」 | 单击 | `kill <slot>`（force-stop）并销毁该 slot 的虚拟显示，slot 归还 |
| 「断开」 | 单击 | 结束全会话（被控端应用不受影响） |

**关于全屏**：进全屏的目的是**打游戏**，所以双击后该路重连为「复用现有主屏投屏参数」（1080P / 30fps 档），其余三路保持缩略图参数。被控端主屏**始终保持熄屏**，不因打开应用而点亮（与 Phone Link 的行为一致：打开再多应用，不点「打开手机屏幕」主屏仍是黑的）。

### 5.2 全屏页

- 悬浮球（**保留原有一切功能**）新增两项：
  - **切换下一个应用** —— 在已占用的 slot 间循环（切 display-id，纯 UI）
  - **回退主页面** —— 回首页（**4 路流保持**，不停流）
- 返回键 / 返回手势：**不拦截**，继续注入被控端

### 5.3 会话管理与 slot 生命周期

**slot 按需启动**（不预建）：

```
点击收藏应用 → holder: create <slot>（建虚拟显示）→ launch <slot> <pkg>
             → 主控端 scrcpy --display-id=<id> 连接该路
关闭选中应用 → holder: kill <slot>（force-stop）→ destroy <slot>（销毁虚拟显示）→ 资源归还
```

- 每个 slot **独占**一路 scrcpy session（`--display-id=<holder 分配的 id>`）
- **必须给每路显式指定不同的 `--port`**（实测：scrcpy server 默认端口段会冲突，导致第 4 路失败）
- 缩略图刷新：1fps 低码率；双击全屏 → 该路重连为高档参数，其余三路不变
- 传输分辨率：虚拟显示**始终原生分辨率**；传输参数见 §5.4

### 5.4 编码与画质策略（实测依据）

**编码器**

- scrcpy 默认自动选择**硬件编码器**。实测 4 路并发时**全部命中** `c2.mtk.avc.encoder`，无一路退化到软编
- **不要硬编码编码器名**：MTK / 骁龙 / 麒麟的 vendor 编码器命名各不相同。依赖 scrcpy 的自动选择，并在设置里提供可选的显式覆盖
- 软编代价约为硬编的 **9 倍**（实测：单路软编 `22%user+48%sys` = 70% CPU；4 路硬编合计仅 33%）

**分辨率与帧率**

- **虚拟显示始终用原生分辨率**（改了应用可能异常），与传输分辨率无关
- 传输参数三件套：`--max-size` / `--max-fps` / `--video-bit-rate`
- **scrcpy 不支持运行时修改分辨率或帧率**（控制协议里没有这类消息）→ 全屏要提画质只能**重连该路**

| 状态 | 建议参数 | 说明 |
|---|---|---|
| 缩略图（四宫格） | 720p @ 1fps @ ~1Mbps/路 | 低帧率下每帧码率充裕，720p 已足够清晰；4 路 ≈ 4Mbps |
| 全屏（打游戏） | **复用现有主屏投屏参数（1080P 档）** | 需重连该路，约 1~2 秒 |
| 全屏（仅查看） | 沿用缩略图参数 | 不重连，省带宽 |

以上缩略图参数**放进设置页可配置**（分辨率 / 帧率 / 码率），不同网络环境下按需调整。

**核心红利**：全屏重连**只重建投屏通道，不影响被控端应用**（应用始终跑在 holder 的虚拟显示上）。传统方案里「重连」等于应用重启，这里只是一次秒级重连。

## 7. 容量与风险

| 项 | 说明 |
|---|---|
| **内存** | 手机 11.3GB，当前已用 10.9GB（含缓存）。**4 个大型游戏同时跑有 OOM 风险**；混合用途（1~2 游戏 + 微信等轻型应用）压力小得多。UI 允许 4 格，实际数量按内存预算决定 |
| **CPU** | 4 路 540p 编码实测 CPU 开销很小（722% idle），不是瓶颈 |
| **端口** | 每路 session 必须显式指定不同 `--port` |
| **holder 被 kill** | 显示随之销毁 → 应用被踢回主显示暂停。**必须靠守护进程自动重建**，这是「主控退出继续跑」的命门 |
| **游戏对显示环境的敏感度** | 实测某 Unity 手游正常。其他游戏（尤其对显示切换敏感的）需逐个验证 |
| **应用自身行为** | 部分应用在虚拟显示上可能功能受限（如依赖物理屏幕特性、或拒绝在非默认显示运行） |

## 9. 分期与验收标准

### 一期：holder + 单应用闭环

- Magisk 模块内实现 display-holder（创建/持有/命令/守护）
- 主控端：首页应用列表 → 点击启动到虚拟显示 → 全屏 → 悬浮球回列表
- **验收**：
  1. 点应用能在被控端对应虚拟显示上拉起并投屏
  2. 主控端**退出应用**后，被控端应用进程存活、重连后画面恢复
  3. holder 被 kill 后自动重启并重建显示

### 二期：四宫格多会话

- 4 路 session 管理（含 `--port` 分配）
- 四宫格 UI（单击选中 / 双击全屏 / 1fps 缩略）
- 悬浮球「切换下一个」
- 操作栏三按钮
- **验收**：
  1. 4 个 slot 各自跑不同应用、互不干扰
  2. 双击全屏与返回列表瞬时完成（不重建 session）
  3. 「关闭选中」后该 slot 释放、其余不受影响
  4. 主控端来回切换 10 次，被控端应用不重启

### 三期：公开整理

- 合并仓库、脱敏、补文档、CI
- **验收**：全历史扫描零隐私命中；陌生人能按 README 从零跑通

## 10. 决策记录（2026-10-07 定稿）

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| 1 | holder 命令通道 | **命令文件** `/data/local/tmp/display-holder/cmd` | 主控端本就通过 adb shell 通道操作，追加一行最简单可靠；不需要 socket 的实时性 |
| 2 | slot 分配 | **每个应用独占一个 slot，按需启动** | 点击时才创建虚拟显示并拉起应用；关闭即销毁、资源归还 |
| 3 | 「手机主页」 | **独立、不占 slot、按需创建、退出即销毁** | 与 Phone Link 的「打开手机屏幕」一致；若占 slot 会挤掉挂机位 |
| 4 | 全屏行为 | **重连升级为高档参数**（复用现有主屏投屏参数 1080P） | 全屏目的是打游戏，1fps 缩略图无法操作 |
| 5 | 缩略图参数 | **设置页可配置**（分辨率/帧率/码率） | 不同网络环境需求不同 |
| 6 | 编码器选择 | **依赖 scrcpy 自动选择**（硬件优先）+ 设置里可选显式覆盖 | 不同 SoC 的 vendor 编码器命名不同，硬编码不可移植 |
| 7 | 被控端主屏 | **始终保持熄屏**，不因打开应用而点亮 | 虚拟显示不接管主屏；与 Phone Link 行为一致，省电且不打扰 |
| 8 | 返回键/手势 | **不拦截**，继续注入被控端 | 游戏内返回操作需要正常传达 |

**后续（不在本期范围）**：自动点击 / 脚本化操作（虚拟显示上的输入注入）。
